# Music Lab — roadmap разработки для AI-агента

**Зафиксирован:** 19.10.2026. **Приоритет:** стабильное воспроизведение → данные и инфраструктура → каталог и перенос → рекомендации → оформление.
**Статус:** план, не отчёт о готовности. Исходная точка — прототип Music Lab 0.7.x. Ранее созданный [PLAN.md](PLAN.md) сохраняется как исторический план; для следующей разработки приоритетен этот roadmap по новому решению пользователя.

## Как агент должен работать

1. **При каждом запуске** прочитать [AGENTS.md](AGENTS.md), этот файл, открытые PR/issues и состояние `main`. Актуальный серверный клиент — `integration/music-search`; корневой `index.html` — старый прототип. Не считать функциональность из открытого Draft PR слитой или доступной пользователю.
2. Двигаться **сверху вниз: P0 → P1 → P2 → P3**. Брать первую незавершённую задачу, проверять уже существующий код и не реализовывать её повторно. Разбивать крупную задачу на небольшие самостоятельные PR с тестами и чёткими критериями приёмки. Разрешены независимые подготовительные работы, но не в ущерб критическим блокерам.
3. Для каждого PR: воспроизвести проблему/описать ожидаемое поведение → изменить код → добавить регрессионные тесты → запустить все применимые проверки → проверить сценарий вручную там, где доступно → обновить статус ниже и приложить подтверждения. **Только после фактической проверки** ставить `[x]`. Непроверенное на iPhone помечать как **«ожидает iPhone»**, не как выполненное.
4. Работать автономно в рамках согласованных задач: не спрашивать разрешения на обычные исправления, рефакторинг, тесты и документацию. При юридических ограничениях API, затратах, создании внешних аккаунтов, существенной смене стека, публикации пользовательских данных и потенциально разрушительных операциях — остановиться и согласовать решение. Следующая сессия агента должна продолжать с первой незавершённой задачи; этот файл **не запускает агента в фоне**.
5. **Не терять данные и доступ.** GitHub — источник истины; изменения через ветку и PR, без ZIP и новых копий установки; сохранять существующие `localStorage`, настройки, окружение, библиотеку и рабочую ссылку. Перед миграцией делать резервную копию и иметь откат. Не публиковать токены, cookies, ключи, приватные URL, аудиофайлы без прав.
6. Проверки backend: `python -m unittest discover -s integration/music-search/tests`, применимые Node/JS-тесты, позже Playwright и iPhone smoke. Не объявлять браузерный или mock-тест доказательством работы фонового звука в Telegram на iPhone.
7. **После каждого шага** оставлять в PR: что реализовано, тесты, что проверено на iPhone, ограничения, следующий пункт roadmap. Обновлять чекбоксы только для законченных пунктов. Не отмечать весь этап выполненным при частичной реализации.

## Этап 0 — упорядочить разработку и защитить данные (P0)

- [ ] Разобрать цепочку незавершённых PR, в том числе [#4](https://github.com/mnlghtooi/tg_music_app/pull/4), [#6](https://github.com/mnlghtooi/tg_music_app/pull/6), [#7](https://github.com/mnlghtooi/tg_music_app/pull/7), [#9](https://github.com/mnlghtooi/tg_music_app/pull/9). Определить фактически активный код; согласованно интегрировать проверенные изменения без потери функций.
- [ ] Сделать резервную копию библиотеки до изменений структуры хранения; проверить восстановление и сохранение плейлистов/избранного.
- [ ] Подключить к CI **все** существующие Python и Node-тесты; зафиксировать базовые проверки iPhone и метрики старта, перемотки, переключения, ошибок.

**Готово:** известны активная версия и открытые ограничения, есть регрессионный baseline и проверенный способ сохранить данные.

## Этап 1 — исправить воспроизведение (P0, начинать в первую очередь после baseline)

- [ ] **Перемотка:** исправить текущий ползунок (он уже есть в коде); диагностировать `duration/seekable/buffered`, HLS, MP3 Range/206, `seeking/seeked`, системный seek. Проверить 10/50/90% трека на iPhone.
- [ ] **Доступность:** ввести `playable / preview_only / blocked / unknown / temporary_error`; не показывать подтверждённо недоступные и 30-секундные превью как полные треки. Не скрывать настоящие короткие треки только по длительности; не обходить DRM и платный доступ.
- [ ] **Изоляция плеера:** единый PlayerController и состояние очереди вне экранов. Поиск, просмотр артиста, плейлистов, импорт и смена вкладок не должны останавливать звук.
- [ ] **Системные прерывания:** различать нажатую пользователем паузу и паузу от таймера/звонка/уведомления; корректно пытаться возобновить по возможности Telegram/iOS. Если WebView не позволяет autoplay — честное восстановление по нажатию, без бесконечных попыток.
- [ ] **Переход между треками:** подготовка следующего URL/метаданных, затем тест разрешённой предзагрузки ~5 секунд, отмена устаревшего буфера, измерение пауз/трафика. Не полагаться на `preload=auto` как гарантию.
- [ ] Добавить безопасные диагностические события плеера и автотесты регрессии, выполнить отдельную матрицу iPhone: таймер, блокировка, Bluetooth, Wi-Fi/сотовая сеть, Next/Previous, seek.

**Готово:** полные доступные треки воспроизводятся и перематываются, поиск не прерывает звук, следующий трек стартует стабильно; известные ограничения iOS задокументированы.

## Этап 2 — постоянная работа приложения и библиотека (P0/P1)

- [ ] Постоянный HTTPS-хостинг Python backend и стабильная ссылка Mini App; CI/CD с тестами, деплоем и откатом. Не путать GitHub Pages, локальный сервер, Quick Tunnel и реальный прод.
- [ ] Серверная библиотека (для старта SQLite или PostgreSQL по фактической потребности), безопасная авторизация Telegram через проверку `initData`; сохранение лайков, дизлайков, плейлистов, настроек и очереди.
- [ ] Безопасный перенос текущего `localStorage` на сервер, идемпотентность, экспорт/импорт JSON и резервное копирование; проверить смену устройства/домена.
- [ ] Лимиты запросов, безопасный медиапрокси, таймауты, retry без обхода 429/403, мониторинг ошибок и доступности источников с IP хостинга.

**Готово:** приложение доступно по одной постоянной ссылке, данные пользователя сохраняются после обновления/смены устройства, релиз можно откатить.

## Этап 3 — качественный каталог, поиск, артисты (P1)

- [ ] Единые сущности Artist / Recording / Release / ProviderTrack; связывать разные источники только по подтверждённым метаданным/ID, не путать оригинал с кавером, live или remix. Оценить MusicBrainz для идентификаторов и Discogs для дискографии (не для аудио).
- [ ] Довести существующие фильтры **Всё / Артисты / Альбомы / Плейлисты / Треки** ([issue #1](https://github.com/mnlghtooi/tg_music_app/issues/1)): релевантность, проверка доступности, нормализация и дедупликация, корректная пагинация, ошибки и сохранение результатов; поиск по всем поддерживаемым источникам по умолчанию.
- [ ] Довести существующие карточки артиста/альбома/плейлиста: описание, релизы, дискография, треклист, переходы назад, воспроизведение без прерываний. Не выдавать профиль пользователя SoundCloud за подтверждённого артиста.
- [ ] Исправить загрузку обложек: обработка ошибок, допустимые источники, аккуратные локальные стильные fallback-обложки и lazy loading.
- [ ] Довести UX «Моя музыка» ([issue #2](https://github.com/mnlghtooi/tg_music_app/issues/2)): видимые списки избранного/плейлистов, мультивыбор плейлистов, понятные действия и сохранение очереди.

**Готово:** поиск возвращает релевантные пригодные записи; карточки и библиотека работают связно и не ломают воспроизведение.

## Этап 4 — качественный перенос и источники (P1)

- [ ] Доработать существующий импорт **публичных Spotify-плейлистов**: полнота и большие списки, сопоставление по названию/артисту/версии/длительности/ISRC при наличии; не считать совпадение метаданных доказательством совпадения аудио.
- [ ] Подтверждать спорные записи, исключать неверные каверы/ремиксы/превью, отдельно показывать ненайденное и ошибки источников; сохранять прогресс и продолжать прерванные задачи; повторный импорт не дублирует данные.
- [ ] Исследовать разрешённый перенос **Яндекс Музыки** сначала на метаданных публичных плейлистов, без обещаний неподтверждённого API. Экспорт исходного списка и импорт собственной библиотеки — разные функции.
- [ ] Оценить официальную доступность каталогов SoundCloud/Audius/Bandcamp и интеграций VK/YouTube/Spotify; не добавлять скачивание/стриминг без подтверждённых прав и условий API. Discogs и MusicBrainz — метаданные, не потоковое аудио.

**Готово:** несколько разнокалиберных плейлистов переносятся с отчётом, подтверждением сомнений и сохранением данных; неподдерживаемые площадки помечены честно.

## Этап 5 — радио по треку и рекомендации (P2)

- [ ] Реализовать режим **«Радио по треку»** с автопополнением очереди похожих **доступных** треков без частых повторов и перебоев.
- [ ] Комбинировать разрешённые related-сигналы источников с собственным ранжированием по артисту, жанру, эпохе, настроению и новизне; не считать наличие ready-made рекомендаций у каждого сервиса гарантированным.
- [ ] Учитывать лайки/дизлайки, историю и пропуски; исключать дубликаты и недоступное. Начать с правил и измерений, без преждевременного ML.
- [ ] Измерять качество: доступность, skips, повторы, добавления в избранное и разнообразие; проверить холодный старт без истории.

**Готово:** после одного трека играет непрерывный, разнообразный поток; пользовательские оценки влияют на очередь.

## Этап 6 — главная и автоматические подборки (P2)

- [ ] Пять подборок дня по жанрам/исполнителям, обновляемых сервером без ручного вмешательства.
- [ ] Плейлисты **по эпохам**, **новинки** по настоящим датам релиза, а не дате загрузки на площадку.
- [ ] Потоки **по настроению** и настройка степени новизны; позже персонализация на основе истории.
- [ ] Кеш, обновление подборок по расписанию, защита от дубликатов, проверка доступности перед показом.

**Готово:** главная автоматически предлагает актуальные, воспроизводимые подборки.

## Этап 7 — Telegram, звук и визуальная полировка (P3)

- [ ] **Поделиться треком в Telegram**: оставить отправку публичной ссылки. Отдельно реализовать отправку разрешённого аудиофайла при наличии прав и работающего сценария; измерить этапы подготовки/загрузки, кешировать Telegram `file_id` для повторной отправки. Учитывать лимит обычного Bot API `sendAudio` 50 МБ; не перекодировать без необходимости.
- [ ] Сначала минимизировать паузу между песнями (gapless); затем исследовать опциональный **crossfade** (3/5/8 с) с учётом реальной поддержки iPhone/Telegram WebView, безопасный fallback.
- [ ] Единые компоненты плеера, поиска, библиотеки, модалок и обложек; safe-area iPhone, skeleton/loading/error, анимации, доступность.
- [ ] Финальная регрессия на телефоне, наушниках, блокировке, длительных плейлистах и на реальном хостинге.

**Готово:** удобный и устойчивый продукт; неподтверждённые возможности платформы не выдаются за готовые.

## Текущий следующий шаг для агента

**Сначала выполнить этап 0: аудит веток/PR, сохранность библиотеки и CI; затем — этап 1, начиная с перемотки и недоступных треков.** Не начинать новые рекомендации или визуальные фичи до устранения критических проблем. Если существующие PR уже содержат частичные решения, продолжать и проверять их, а не переписывать заново.

**Отчёт о каждой итерации:** ссылка на PR/коммит; закрытые пункты; результаты тестов; статус iPhone-проверки; блокеры; конкретная следующая задача.
