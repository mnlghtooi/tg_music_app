# Правила работы с Music Lab

## Обновления и запуск — постоянное правило пользователя

- GitHub — источник истины для кода. Новые изменения оформлять через ветку и pull request.
- Не предлагать пользователю скачивать ZIP, распаковывать новые версии, создавать очередные копии приложения или вручную переносить файлы. Исключение — только прямой запрос пользователя.
- Для локальной работы обновлять одну существующую рабочую папку самостоятельно, сохраняя библиотеку, настройки и окружение. Перед заменой изменённых пользователем файлов проверить различия и сохранить резервную копию.
- Известная рабочая папка на ПК пользователя: C:\Users\moonlight\Documents\Codex\2026-10-18\new-chat\outputs\music-search. Сначала проверить её наличие; не создавать новую пользовательскую копию взамен существующей.
- Пользователь запускает прежний START.cmd. Если окружение или запуск сломаны, исправлять их в существующей установке, а не отправлять пользователя за новым архивом.
- Для уже размещённого приложения обновлять подключённый сервер из репозитория; пользователь продолжает пользоваться прежней ссылкой.
- Не утверждать, что приложение обновлено или доступно в Telegram, только потому что создан PR. Проверять фактическую рабочую папку/ветку сервиса, запуск и доступность.
- Различать: код в GitHub, обновлённая локальная установка, работающий локальный сервер, временный HTTPS-туннель и постоянный хостинг. Если хостинг ещё не подключён, сказать об этом прямо.
- Не оставлять запуск на пользователе, когда агент может выполнить разрешённое обновление и проверку сам. Сообщать точное оставшееся действие: например, перезапуск прежнего START.cmd.
- Это правило относится к выдаче и обновлению приложения; необходимые зависимости устанавливать автоматически в существующее окружение, не выдавать их за готовое приложение.

## Проверка и сохранность

- Актуальный серверный клиент — integration/music-search; корневой index.html является отдельным старым статическим клиентом.
- Перед продолжением проверить состояние веток и PR с Bandcamp; не считать незавершённый PR слитым.
- Сохранять пользовательские данные и секреты. Не печатать ключи, cookies или полную личную /open/ ссылку в отчётах и не коммитить их.
- Менять только третью цифру версии без отдельного разрешения на изменение второй.
- Для серверных изменений запускать: python -m unittest discover -s integration/music-search/tests.
- Не объявлять проверку на ПК подтверждением работы на iPhone, в Telegram WebView или с IP хостинга.
