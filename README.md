## Где рабочий код

Приложение и Python-сервер находятся в [`integration/music-search/`](integration/music-search/). Там же зависимости, тесты, журнал изменений и список ручных проверок. ZIP-файлы не являются исходным проектом и не нужны для обновления размещённого сервера.

| Файл | Назначение |
|---|---|
| index.html в integration/music-search | Актуальный интерфейс, библиотека и браузерный плеер |
| server.py | HTTP API, личная сессия доступа, media proxy и точка запуска хостинга |
| search_service.py / stream_service.py | Поиск SoundCloud и подготовка одного аудиопотока |
| bandcamp_service.py | Экспериментальный поиск, страницы релизов и публичное аудио Bandcamp |
| START.cmd / launch.py | Локальное окружение Windows, браузер и попытка временного HTTPS-туннеля |
| prepare_assets.py | Подготовка закреплённой библиотеки hls.js для чистого клона/сборки |
| requirements.txt / tests | Зависимости и автоматические проверки |
| render.yaml в корне | Конфигурация будущего размещения, не уже работающий хостинг |

Корневой `index.html` — ранее опубликованная статическая версия для GitHub Pages. Она не запускает Python и автоматически не переключается на серверную версию. Описание старого теста с синтезированным WAV больше не является описанием всего приложения.

## Запуск из репозитория на Windows

1. Клонировать репозиторий или обновить существующую копию через `git pull`.
2. Открыть `integration/music-search/START.cmd`.
3. Скрипт установит зависимости и откроет текущую личную ссылку приложения. Окно сервера должно оставаться открытым.

Без Windows-лаунчера, из каталога `integration/music-search`:

```sh
python -m pip install -r requirements.txt
python prepare_assets.py
python server.py
```

Открыть напечатанную сервером ссылку `/open/...`. Локально сервер слушает только `127.0.0.1`.

## Постоянный запуск в Telegram

Схема: **Telegram → HTTPS-сервис → приложение и Python API → музыкальный источник**.

Исходники хранятся в GitHub. Работает сервер на Python-хостинге. GitHub Pages публикует статический HTML/JS и не исполняет этот backend.

В корне добавлен [`render.yaml`](render.yaml) для пробного размещения прямо из репозитория:

1. После merge PR подключить этот репозиторий в Render через New → Blueprint. Перед созданием проверить выбранный тариф: конфигурация запрашивает Free.
2. Render установит зависимости, подготовит закреплённый hls.js и запустит сервер. `/healthz` — проверка готовности без доступа к музыкальному API.
3. Сервис получит HTTPS-адрес. Ключ `MUSICLAB_ACCESS_KEY` создаётся в настройках сервиса, не хранится в GitHub и остаётся постоянным между деплоями.
4. Для личного теста использовать `https://<адрес-сервиса>/open/<ключ>` как ссылку Mini App в @BotFather → `/setmenubutton` для @mnlgth_music_app_bot. Любой получивший эту ссылку получает доступ к личному тестовому серверу; её не следует публиковать для общего доступа. Для публичного многопользовательского запуска ещё нужна проверка Telegram initData.
5. После настройки новые merge в `main` запускают обновление на стороне хостинга. Скачивать архив и держать свой ПК включённым не потребуется.

**Развёртывание ещё не выполнено:** хостинг-аккаунт не подключён, адрес меню Telegram не изменён. Проверки на локальном ПК не подтверждают доступность музыкальных источников с IP хостинга. Free-сервис может засыпать и задерживать первый запрос; условия хостинга нужно проверить перед созданием сервиса. Библиотека пока в localStorage: новый домен не переносит сохранения автоматически.

## Как пользоваться с iPhone во время локальной отладки

1. Запустить актуальный START.cmd на Windows. Он запускает сервер, открывает локальную ссылку Computer и пытается поднять временный HTTPS-туннель Cloudflare.
2. Только если в окне появился **PHONE_URL=https://…/open/…**, открыть эту полную личную ссылку на iPhone. `127.0.0.1` с iPhone не ведёт на Windows-ПК.
3. Открытие PHONE_URL в Safari — проверка в браузере. Чтобы проверить **внутри Telegram**, установить эту HTTPS-ссылку как URL кнопки меню бота через @BotFather → `/setmenubutton` → @mnlgth_music_app_bot.
4. START.cmd **сам не меняет меню бота**. В этой сессии адрес бота не обновлялся. Старый URL GitHub Pages по-прежнему откроет старый интерфейс.
5. ПК, интернет, сервер и туннель должны оставаться работающими. При перезапуске меняется случайный ключ локального сервера, а у временного туннеля может измениться домен; старую ссылку нельзя считать постоянной.

Туннель в одной из проверок среды вернул 502. Наличие PHONE_URL в выводе не заменяет проверку его открытия и воспроизведения на телефоне. Если туннель недоступен, локальная проверка на ПК остаётся возможной. Хостинг не является текущей обязательной задачей: пользователь подтвердил, что пока дебажимся локально.

## Что реализовано

### Интерфейс и библиотека

- Поиск отдельной кнопкой в правом верхнем углу; отдельный экран, восстановление предыдущего запроса и результатов.
- В разделе «Плейлисты» кнопка создания — `+` справа сверху; без отдельной лишней кнопки «Избранное» в заголовке. Любимые треки остаются частью библиотеки.
- Плейлист открывается на отдельном просторном экране; назад — стрелка без текста; нумерация внутри пользовательского плейлиста убрана.
- Действия плейлиста находятся внутри в меню `…`; у треков своё меню `…`.
- Лайки, дизлайки, создание/изменение плейлистов, очередь, ручное/автоматическое переключение.
- Подсветка текущего трека в поиске, коллекциях, очереди и библиотеке.
- Нижний мини-плеер и полный экран плеера по нажатию на плашку трека.
- Лоадер **на месте Play** в мини-плеере и полном плеере: немедленный отклик на выбор, ожидание данных и перемотку; Playing показывает Pause, ошибка/пауза возвращает Play. Быстрое переключение не должно оставлять состояние старого трека.
- Хранение библиотеки в **localStorage**. Пока нет серверной БД, синхронизации устройств и автоматического переноса между доменами/портами. Новая ссылка туннеля может означать другое хранилище — не считать это удалением прежней библиотеки.
- Media Session: метаданные, play/pause/next/previous/seek. Лайк/дизлайк с экрана блокировки **не реализованы** и остаются требованием, см. LOCK_SCREEN.md.

### SoundCloud и оптимизации

- Гостевой поиск через публичный веб-эндпоинт SoundCloud, без платного API-ключа и логина. Это не официальный стабильный контракт API; не обещать полный каталог или доступность каждого трека.
- Единая выдача треков, профилей и плейлистов в порядке источника. Подписи «Исполнитель» и «Плейлист»; треки без подписи типа. Профиль может не быть подтверждённым артистом и не иметь треков.
- Исполнитель/плейлист открывает публичные треки. По 10 **суммарных результатов** на странице, кеш 5 минут, защита от устаревших ответов, сохранение исходной выдачи при возврате. Листание не меняет проигрывание.
- Ранняя версия через yt-dlp тормозила: разные поиски держали общую сетевую блокировку. Поиск вынесен в search_service.py: постоянный httpx.Client, HTTP/2, параллельность, объединение одинаковых запросов, прямое преобразование JSON. yt-dlp остаётся для начального получения публичного client_id.
- Пять поисков до/после при прогретом сервере и пустом кеше страниц: 4.7–11.1 с → 0.22–0.58 с; медиана 5.085 → 0.486 с. Это наблюдения одной сети, не SLA и не время холодного запуска.
- HLS уже загружал аудио частями. Долгий старт объяснялся дополнительным извлечением адресов нескольких форматов и расходами media proxy. stream_service.py переиспользует метаданные поиска/плейлиста, выбирает один доступный формат, кеширует адрес и объединяет запросы одного трека.
- Прокси переиспользует соединения, отдаёт бинарное аудио по 16 KiB с Range/Content-Range. В hls.js целевой запас 20 с, верхняя настройка 30 с; на iPhone native HLS и объём буфера контролирует ОС.
- Реальный старт Horizons из плейлиста: старый backend 4.509 с → новый 1.546 с; повтор 2.112 с, до currentTime > 0.2 с. При начале было около 20 с буфера вместо всего трека. Перемотка на 120 с возобновилась за 0.79 с.
- BLOCK-записи помечены недоступными и не включаются в очередь страницы. Превью обозначаются отдельно. Платные/приватные/DRM-ограничения не обходятся. Импорт чужого плейлиста целиком в библиотеку не добавлен.

### Bandcamp: сделано и ограничение

- Добавлены источник, смешанный поиск треков/исполнителей/альбомов, страницы по 10 внутри подборки **до 50**, исполнитель → релизы → альбом → треки, вложенный возврат.
- Публичный MP3-128 передаётся через тот же плеер с перемоткой, лоадером и лайками. Стабильные ID позволяют заново получить страницу сохранённого трека. Private/capped/недоступные записи не воспроизводятся.
- Ранее живой Chrome-тест прошёл: Scott Buckley → Library Songs 5 → Horizons, длительность 293.369705 с; поиск 0.675 с, запуск до currentTime > 0.5 с за 1.256 с; перемотка, лайк, возврат и пауза работали.
- **Повтор 19.10.2026:** поиск отвечал за 0.432–0.642 с, но страницы артиста и альбома вернули **Client Challenge**. Полный повторный тест не прошёл. Показывается ошибка; защита автоматически не решается.
- Следовательно, Bandcamp — экспериментальная интеграция в draft PR, а не гарантированно работающий источник. Перепроверить в целевой сети; не путать наличие пункта меню с подтверждённым воспроизведением.
